# Venture OS — Phase 0: one company identity, one decorative code

Status: **foundation landed (code + vocabulary + read-only map); the storage
conversion is NOT run.** Decisions taken here are marked *assumed* and await
ratification.

This is the Ventures half of the Phase 0 that stabilizes identity before any
feature work on the pillar. It answers one question and fixes one column.

## 1. What the code is today

`ventures.venture_id` holds a **code**: `VNT-` followed by 8 uppercase hex
characters, generated by `generateVentureId()` in
`src/services/ventures/intake.js` (e.g. `VNT-A1B2C3D4`).

The code is **not decorative today**. It is a real, `UNIQUE` column, and on the
older generation of the table (`src/migrations/010_ventures.sql`) it is the
**foreign-key target** child rows store. The newer generation
(`src/migrations/venture_os_track1_foundation.sql`) keys children on
`ventures(id)` instead. Both live in the same database, so the same
relationship is written with the code in some tables and the internal id in
others — and a join can only cross them through an `OR` bridge:

```
JOIN ventures v ON (x.venture_id::text = v.id::text OR x.venture_id::text = v.venture_id)
```

Two sites carry that bridge today
(`src/models/ventureWorkspace/milestonesAndAccess.js`,
`.../journeyAndReports/tasksAndSubmissions.js`). They are the symptom this phase
removes.

## 2. The target — a decision, not a description

| Role | Column | Used for |
|---|---|---|
| **Internal identifier** | `ventures.id` — a **UUID** | every STORED relationship; nothing else |
| **Decorative code** | `ventures.venture_id` — `VNT-…` | the key people and routes USE (URLs, API paths) |

Decisions (product, confirmed):

- **The internal id is a UUID, unified across both databases.** Production's
  `ventures.id` is an `INTEGER` today (`migrations/audit_venture_id_types.sql`);
  staging's is a UUID. The target is UUID everywhere.
- **The code stays the access key.** Routes keep taking `VNT-…`, so no URL
  changes. The code simply stops being *stored* as a relationship.
- **The storage is unified**: every child column holds the internal id.

## 4. What is NOT done (and why)

### 4.1 The foreign keys that pin the code — found on staging

Several code-holding tables declare their foreign key **to the code column**,
not to the internal id:

```sql
venture_id TEXT NOT NULL REFERENCES ventures(venture_id) ON DELETE CASCADE
```

That is true of `venture_members`, `venture_history`, `venture_activity_log`,
`venture_founders`, `venture_origins`, `venture_sessions`, `venture_tasks`,
`venture_staff_assignments`, `venture_verifications`, `venture_reports`,
`venture_notes`, `venture_operating_plans`, `integration_configs`, `webhooks`…
(see `migrations/venture_phase1_foundation.sql` and
`migrations/venture_schema_align.sql`).

**Consequence:** writing the internal id into such a column violates the
constraint — a plain `UPDATE` fails. Unifying one of those columns means, in
this order:

1. drop the foreign key to `ventures(venture_id)`,
2. rewrite the values (code → internal id),
3. **retype** the column to match `ventures.id` (uuid on staging, integer on
   production) — the FK target and the FK column must share a type,
4. recreate the foreign key against `ventures(id)`.

Columns *without* such a foreign key only need step 2. The script
(`scripts/migrations/apply_venture_identity_phase0.mjs`) now detects which is
which and runs the right plan; the id-type conversion (§4.4) is therefore not a
separate later step for these columns — it happens with them.

### 4.2 The coupling — read this before deploying anything

Reads and writes must flip **together**, and only after the storage is unified.
There is no safe partial state, because the two conventions cannot coexist in
one column without the bridge:

| State | Result |
|---|---|
| Readers on the internal id, data still holding codes | every join returns nothing — empty directories, refused access |
| Readers flipped, writers still posting codes | new rows are orphans, invisible to the flipped readers |

So the one sequence that works is:

1. **Convert the WRITES** (below) so a new row carries the internal id.
2. **Run the script** (`npm run db:venture-identity -- --apply`) — the existing
   rows adopt the internal id. Do it in a short window: between the script and
   the deploy of step 3, the running (old) code still writes codes.
3. **Deploy** the flipped readers + writers + the removed bridges together.

### 4.3 What is left — the WRITERS (and direct child filters)

The readers are done (§3). What remains is every place that **writes** a venture
reference, or **filters a child table directly by the code** (not through a join
to `ventures`). They are numerous (~40 sites) and each needs its caller read —
which is why they are NOT guessed at here. Find them with:

```bash
# writers: a child row created from a code parameter
grep -rn "INSERT INTO venture_[a-z_]*" src/models | grep venture_id
# direct filters keyed by the code (the parameter name is the tell)
grep -rn "venture_id = ?" src/models
```

Known examples, each carrying the code today:
`models/ventureActivityStore.js` (`insertVentureActivity`,
`insertVentureHistory`, `selectFounderContactIds`),
`models/ventureMembers.js` inserts, `models/ventureCoachStore.js`
(`insertCoachAssignment`), `models/ventureAccessStore.js`
(`selectViewerRelationship`), `models/ventureWorkspace/*`
(`listActiveVentureAssignmentsForAccess`, `countVentureFoundersByCode` — the
progress route even comments "venture_members stores venture_id as the VNT
code").

### 4.4 The id TYPE

`--plan-convert-id` prints, read-only, what converting `ventures.id` from
INTEGER to UUID would drag along (the foreign keys to drop and recreate, the
referencing columns to retype). A uuid column cannot point at an integer one, so
this step moves the children's TYPES too — a maintenance-window operation to
rehearse on staging, not a runtime self-heal. The joins written in §3 use
`X.venture_id = v.id::text`; when the child columns become uuid, they become
`X.venture_id = v.id`.

On staging this is already settled: `ventures.id` is a UUID, so the script
RETYPES the foreign-keyed reference columns to `uuid` and leaves the others as
TEXT holding the uuid string. A writer may therefore pass the internal id as
text in both cases.

### 4.5 The writers — batch status

Two techniques, chosen per site:

- **`ventureRef` resolved inside the statement** — `INSERT … VALUES ((SELECT id
  FROM ventures WHERE venture_id = ? OR id::text = ?), …)`. One statement, no
  extra round-trip, the caller's identifier unchanged, and the mocks of the
existing tests keep lining up. Used for the append-only streams.
- **Resolved once at the boundary** — `resolveVentureInternalId()`
  (`src/services/ventures/identity.js`) when a flow needs the internal id for
  SEVERAL statements (a route that then reads members, assignments and history).
- **Resolved inside the model, with a fallback** —
  `const id = await resolveVentureInternalId(ref)` at the top of a model
  function, `ref` returned unchanged when nothing matches. This is the workhorse:
  every caller (code or internal id) keeps working, the argument arrays and the
  SQL substrings the tests match on stay identical, and a second round-trip is
  the only cost. Used by `ventureMemberInvitations` and `listVentureMembers`.

The resolver lives in the MODEL layer (`@/models/ventureIdentityStore`) so model
files can use it without importing from `@/services` (which would invert the
layering); `@/services/ventures/identity` re-exports it for service callers.

### 4.6 Running `--apply` on a live database

`ALTER COLUMN … TYPE` takes an ACCESS EXCLUSIVE lock. With an app session
connected (a dev server pointing at the same database) the run **deadlocks**
and the transaction rolls back — nothing is written, but nothing progresses
either. The script sets `lock_timeout = 15s` so it fails clearly instead of
hanging. Stop the server first.
