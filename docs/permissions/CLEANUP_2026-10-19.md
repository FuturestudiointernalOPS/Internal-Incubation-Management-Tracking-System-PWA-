## 2. Les deux modèles venture : lequel est utilisé ?

**Les deux, mais pas à égalité.**

| Modèle | Où il décide encore | Volume |
|---|---|---|
| Capacités + portée (`requireVentureScopedAccess`, `venture_own`) | Toutes les routes venture converties : actions, blockers, business model, calendrier, coachs, dashboard, suivis, entretiens, indicateurs, jalons, connaissances, etc. | ~29 fichiers de routes |
| Ancienne matrice `(responsabilité × zone × action)` (`hasVentureCapability`) | `my-access`, `notes`, `ventureMemberAccess` (gestion des fondateurs), l'autorité des jalons, l'autorité de planification des sessions | 5 fichiers de production |

Conclusion : le **nouveau modèle est le modèle dominant**, mais l'ancien n'est
pas inutilisé. Il reste la seule décision pour les notes internes, la gestion
des fondateurs, la planification des sessions et la lecture « mon accès ».
Supprimer l'ancien écran maintenant retirerait la seule administration de ces
quatre décisions. La migration doit se faire décision par décision, avec un
audit de données (voir `docs/AUTHZ_CURRENT_STATE.md` §3).

## 3. Les deux chemins de droits de base : lequel reste ?

Il faut distinguer deux choses qui se ressemblaient.

### 3.1 Les deux implémentations du même étage « base »

| Chemin | État |
|---|---|
| `profile_capabilities` via le profil de la personne ou le profil par défaut de son rôle | **Utilisé.** C'est le seul chemin. |
| `role_capabilities` (ancien repli quand aucun profil ne résolvait) | **Supprimé le 2026-10-19.** |

Une personne sans profil de base n'a désormais **aucun droit de base** (refus
par défaut). C'est volontaire : le rôle nomme un profil par défaut, et ce profil
est la seule source.

### 3.2 Profil de base et affectations contextuelles

Ce ne sont pas deux implémentations du même choix, mais deux couches :

- le **profil de base** donne les droits permanents liés à l'identité
  (par exemple le profil « Staff Default ») ;
- les **affectations contextuelles** donnent des droits liés à une relation
  (fondateur de cette venture, facilitateur de ce programme), recopiés dans les
  droits personnels avec une empreinte de provenance.

Les deux restent nécessaires. Ce qui a été retiré est le repli par rôle, pas la
couche contextuelle.

## 4. Retrait de `role_capabilities`

### Code

- Plus aucune création de table au démarrage.
- Plus aucune lecture par le résolveur ni par le service de perte de droits.
- Suppression de l'action d'écriture `set_role_default` et des lectures
  `?role=` du centre.
- Suppression des écritures de rattrapage dans tous les modules.
- Le point d'entrée de semis ne sème plus de droits par rôle : il sème les
  profils, les plafonds et les responsabilités.
- Les scripts de configuration neuve ne créent plus la table.

### Migration

`migrations/drop_role_capabilities.sql` supprime la table. **À exécuter après
vérification** : la requête de contrôle en tête du fichier doit retourner zéro
ligne (aucune personne sans profil de base ni profil par défaut de rôle).

### Effet observable

Un compte dont le rôle n'a pas de profil par défaut et qui n'a pas de profil
personnel perd ses droits de base. Les trois identités de base
(`super_admin`, `staff`, `member`) ont toutes un profil par défaut semé ; les
anciens libellés contextuels ont été alignés lors de la phase H.

### Scripts historiques

Les scripts de diagnostic courants ont été repointés (`phase-i1-snapshot`,
`phase1-bulk-upload`, `phase3-lms-retired-scan`, `diagnose-*`,
`db-audit/venture-authority-check.sql`). Trois analyses de dry-run restent
volontairement historiques et citent l'ancienne table :
`dryrun-eligibility-policy.mjs`, `dryrun-phase3-staff-config.mjs`,
`simulate-roles.mjs`. Elles décrivent une décision déjà prise et ne doivent pas
être rejouées telles quelles après la migration destructive.

## 5. Droits d'animation : une seule définition

### D'où venait la liste

La liste des droits d'animation était écrite à la main dans
`src/lib/facilitator-permissions.js`, alors que le catalogue central
(`FEATURE_MODULE_CAPABILITY.facilitator`) définissait déjà les mêmes clés avec
leurs libellés, risques et descriptions.

### À quoi elle sert

- Le panneau PM et l'invitation en masse construisent le JSON de permissions
  complet d'un facilitateur (`v2_program_staff.permissions`) ;
- la liste permet de rendre les cases à cocher de l'interface ;
- le catalogue fournit les libellés et les risques que le centre affiche.

### Pourquoi elle avait été recopiée

Elle précède le catalogue central. À l'époque, l'interface et l'invitation en
masse ne pouvaient pas importer le registre serveur sans traverser les couches ;
la copie était le chemin le plus court. Un test maintenait les deux listes
identiques.

### Correction

La définition complète vit maintenant dans
`src/models/authorization/constants/facilitator-capabilities.js` : nom, risque,
clés, libellés, descriptions. Le catalogue général l'importe au lieu de la
recopier, et la liste des clés en est dérivée :

```js
// Dans le catalogue général :
import { FACILITATOR_MODULE } from "./facilitator-capabilities";
// …
facilitator: FACILITATOR_MODULE,

// Dans le fichier dédié :
export const FACILITATOR_CAPABILITY_KEYS = Object.keys(
  FACILITATOR_MODULE.capabilities,
);
```

Il n'y a donc plus deux définitions. Le test de couverture vérifie en plus que
le catalogue référence **le même objet** que le fichier dédié, pas une copie
égale. Il continue par ailleurs à vérifier que chaque droit déclaré est
réellement consulté par une route. Effet de bord corrigé au passage : un droit
de lecture est maintenant enregistré au niveau 1 (`endsWith(".view")`) au lieu
de 2.
